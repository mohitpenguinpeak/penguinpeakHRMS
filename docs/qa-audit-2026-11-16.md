# QA audit and fixes — 16 November 2026

This is a source review, offline workflow test, responsive rendering audit and
Android compilation check. It is not a claim that the product has no remaining
bugs. No live employee records, messages, leave requests or production settings
were changed. Existing Gradle edits and earlier performance/profile work were
preserved.

## Findings fixed

Severity describes user impact, not the size of the code change.

| ID | Category | Severity | Before | After / evidence |
| --- | --- | --- | --- | --- |
| F01 | Functional | High | Dashboard work totals measured first check-in to last check-out, counting checked-out gaps and breaks as work. | Work totals use individual sessions and deduct closed/ongoing breaks. Unit tests cover a split shift and a running break. |
| F02 | Functional | High | Quick check-in used a hardcoded 10:30 start and different grace calculations from Attendance. | Both use configured start time and subtract the configured grace period. |
| F03 | Functional | High | Rechecking in on a legacy record without a session array could drop its first session. | The legacy check-in/out pair is converted to a session before appending another. |
| F04 | Functional | High | Dashboard checkout could proceed during a break, omitted break deductions and skipped half-day classification. | It rejects active breaks, computes net session durations, records break totals and applies the configured half-day threshold. An offline UI test confirms no checkout PATCH is sent during an active break. |
| F05 | Functional | Medium | A record classified Half Day could remain Half Day after subsequent sessions exceeded the threshold. | A non-late record is reclassified Present when its accumulated work reaches the threshold. |
| F06 | Functional | Low | Dashboard could display afternoon time as `15:30 PM`. | Twelve-hour formatting handles noon, midnight and afternoon correctly. |
| F07 | Functional | High | Dashboard post submission used `category`, while Company Wall and the schema use `post_type`. | Submissions use `post_type`, including `general` for ordinary posts. Tested by inspecting the actual HTTP payload. |
| F08 | Functional / reliability | Medium | Repeated clock/post taps could submit overlapping requests; a completed publication could clear a newer draft. | Pending guards suppress duplicate requests; publication clears only the draft that was submitted. UI tests use delayed responses. |
| F09 | Functional / privacy | High | Switching chat while history loaded could display a late response from the previously selected conversation. | Conversation history clears on switching; generation and conversation-ID checks discard obsolete responses. Tested with responses deliberately delivered out of order. |
| F10 | Functional | High | Rapid chat sends could submit duplicates; completing a send could clear another conversation's draft. | A sending guard permits one request; updates target the original conversation and preserve newer draft text. |
| F11 | Security / reliability | High | The singleton task timer, pre-break task and cached logs could survive sign-out and appear in another account. | Explicit and auth-event logout clear account-specific state. A generation check prevents an in-flight log save from restoring it after cleanup. |
| F12 | Functional | Medium | Attendance calendar used requested leave dates even when HR approved a narrower range; monthly targets treated half-day leave as a full day. | Calendar uses the effective approved range. Monthly targets and completion use fractional day equivalents and count overlapping approved halves once. |
| F13 | Functional / usability | High | Break functions existed without controls; an employee with an active break could be blocked from checkout without a way to end it. | Start/End Break controls are reachable, with correct enabled states. Checkout is disabled during an active break. |

| D01 | Mobile layout | High | AdaptiveRow used overall screen width, forcing rows inside narrow desktop cards; long text could overflow. | Layout uses actual content width, text scaling and flexible text. A 280px card in an 1100px viewport is covered. |

| D03 | Mobile layout | Medium | Welcome/organization headers, employee detail rows and progress labels overflowed with long names or larger text. | Headers wrap, detail rows stack at narrow widths and progress labels wrap. |

| N03 | Reliability | Medium | Several quick clock/chat completion paths could update widgets/controllers or show messages after disposal. | Mounted checks precede those updates; stale chat errors are ignored. |

## Coverage and validation

- Dashboard: 320, 390, 768 and 1024 logical pixels, each at 100% and 150% text.
  Tests scroll through the real loaded dashboard instead of checking isolated
  placeholder cards only.
- Attendance, Adjustments, Leave, Tasks, Company Wall and Chat: loaded at 320px
  with 150% text, including content below the first screen. These use an approved
  HR fixture and mostly empty lists. They do not exhaust every role or dataset.
- Additional UI workflows: publish payload/duplicate guard/new draft; checkout
  blocked by an active break; delayed/out-of-order chat requests; break controls
  and detailed attendance table.
- Unit regressions: session/break durations, legacy rows, half-day equivalents,
  noon/midnight formatting, configured lateness, sign-out cleanup and a timer-save
  response arriving after cleanup.
- HTTP, auth storage and realtime Phoenix messages use in-memory fixtures. No
  test workflow submits an employee action to Supabase.
- Existing tests additionally cover authentication/access, HR documents/payslips,
  leave rules, notifications, organization trees, tasks and other mobile layouts.

## Remaining validation and deployment

- No Android device/emulator was connected (`adb devices -l` returned an empty
  list). Touch/keyboard behavior, system permissions, background/resume behavior,
  push delivery and visual acceptance on real devices remain unverified.
- No production end-to-end account/role, database RLS, webhook or Storage audit
  was performed. The offline transport fixtures do not substitute for it.
- No load, battery, screen-reader, localization or very-large-dataset audit was
  performed. Larger text was rendered at 150%; every combination of text size,
  orientation, keyboard, device and workflow has not been covered.
- Attendance still follows the existing device-local clock policy for punches,
  a Monday–Friday monthly target and eight target hours/day. Company-timezone
  enforcement, custom rosters and the monthly target's holiday policy require
  further specification and validation. Performance scorecards separately use
  company timezone and exclude holidays; this audit does not certify those
  policies as identical across every legacy attendance view.
- Historical performance remains calculated from editable source records rather
  than immutable review snapshots, as documented in the feature release guide.
- Existing informational analyzer findings remain. They include older deprecated
  APIs, style findings and BuildContext warnings outside the corrected paths;
  these are not evidence that every legacy async path has been proven safe.
- The Android build retains the existing debug signing configuration for release
  and existing Firebase/Kotlin migration warnings. Store signing has not been
  configured by this audit.

No new SQL migration or backend deployment is required for these QA fixes. Hot
restart the running desktop app, or install the newly built Android APK. The
previous performance migration is still a prerequisite for performance reports.
